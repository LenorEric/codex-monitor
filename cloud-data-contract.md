# Global cloud data contract

Each WebDAV sync root has one unencrypted `data-contract.json` containing `{"dataContractVersion":2}`. This is the authoritative global cloud contract. The app target is `CLOUD_DATA_CONTRACT_VERSION` in `monitor_cloud.py`, also declared as `cloudDataContractVersion` in `package.json` and packaged `version.json`. Object-level format identifiers remain for decoding and validation; they do not independently authorize access or trigger global upgrades.

Every logical cloud operation checks the marker before accessing payloads. It then claims `sync-lock.json` as described below, rechecks the marker, and retains ownership until the entire operation, including nested account, skills, and usage requests, finishes. Busy manual operations report the conflict immediately; automatic fetch and usage sync retry after 30 seconds instead of waiting their normal interval. All coordination and migration requests stay inside the existing single queued/start and outcome notification pair.

- Equal version: permit normal reads and writes under file ownership.
- Lower version, including an absent marker treated as zero: run every pending `CLOUD_DATA_MIGRATIONS` step consecutively, commit each version with conditional PUT, and verify it before proceeding.
- Higher version: block payload reads, writes, destructive overwrite, and passphrase rotation; report that the local script needs an update. Reading the marker itself is necessary to make this decision.
- Invalid metadata, a missing migration, invalid coordination status, or unsupported required locking/conditional updates: stop before payload access. `allowOptimisticWrites` cannot bypass coordination.

Migration 0 to 1 registers the existing saved formats without changing payloads. Migration 1 to 2 adopts the file coordination protocol; it preserves all account, skills, usage, encryption, and historical payloads. Provisioning occurs before migration under the coordination rules below. Released local contract 15 / cloud contract 3 is the baseline. Pending local contract 16 and cloud contract 4 retain quota reset times as Unix seconds. Startup converts saved reset fields and rebuilds derived displays from retained records. Cloud conversion publishes immutable replacement usage payloads, backs up each original head under `migrations/contract-4`, verifies each new head, and commits the contract marker last; failures restore original heads, and retries safely repeat conversion. Remote conversion runs on first cloud access. Released intermediate migrations remain available for sequential upgrades.

## File coordination

The idle file contains `{"writing":0}`. Acquisition first checks for an existing owner, requests native `LOCK` on the file with `Depth: 0` and `Timeout: Second-300`, rereads its strong ETag, and conditionally changes it to `{"writing":0,"owner":"<operation UUID>"}` using `If-Match`. Only the successful claimant may access payloads. This conditional owner claim is required because Jianguoyun can grant independent native lock tokens to multiple clients authenticated as the same account. Native LOCK alone is not sufficient there.

Immediately before the first payload mutation (including directory creation or migration), the owner conditionally changes the file to `{"writing":1,"owner":"<operation UUID>"}`. Further writes and nested calls reuse the same lock and status. At completion or an ordinary exception, cleanup conditionally restores `{"writing":0}` and sends `UNLOCK`. Cleanup failures make the operation fail even if payload changes already completed. The flag means a write operation is active, not that multi-object changes are a transaction or can be rolled back automatically.

Read operations also claim the file so they cannot observe a writer partway through publication or race from reading a stale pointer into writing. Read-only operations leave `writing` at zero, but still update the tiny owner record at acquisition/release. This intentionally spends a few metadata round trips to provide consistent reads. Existing incremental payload selection and conditional GETs still avoid transferring unchanged payloads. No status polling is added between ordinary requests; one owner claim covers the whole operation.

Every protected request includes a tagged `If` condition for the lock-file token. Status updates and release additionally use the latest strong ETag. Finite native leases exceeding 60 seconds are refreshed halfway through, or before less than 60 seconds remain, allowing headroom around 30-second HTTP calls. An expired lease stops further access and is never silently reacquired. Infinite native leases are accepted for Jianguoyun compatibility. An owned status file is never stolen automatically, even after a finite native lease expires, so a delayed or stalled writer cannot overlap a replacement owner.

On first use only, a missing file is provisioned through an atomic `MKCOL .sync-lock-init` gate, rechecking absence after acquiring that gate. This avoids depending on `If-None-Match: *`, which Jianguoyun may ignore on PUT. The gate is removed after provisioning. It is a one-time initialization guard, not a recursive directory LOCK or a normal-operation lock. Existing or malformed lock files are never silently overwritten.

Cloud overwrite preserves `data-contract.json`, `sync-lock.json`, and `.sync-lock-init`. Passphrase rotation leaves these unencrypted coordination files unchanged. The lock file contains no credentials or payload content.

## Interruption and recovery

A crash or lost response may leave an owner record, `writing:1`, an initialization gate, or an infinite server lock. Automatic recovery never guesses that an owner is dead or clears another owner's record. Stop all participating clients, inspect retained sources and any interrupted account/passphrase operation, restore a consistent cloud state, release server locks through the provider if needed, then restore the file to `{"writing":0}` and remove a stranded initialization gate. Preserve originals before repair. Do not clear status while any participant could still be running.

The protocol prevents overlapping operations among updated, cooperating clients on a service that enforces atomic MKCOL and strong ETag `If-Match`. It does not prevent manual edits or software bypassing the coordination file. Upgrade all participating clients before using the new protocol. Released cloud-contract-1 clients reject marker 2; during transition, a conforming server's old recursive root lock conflicts with the new file lock. Pre-contract clients cannot enforce the version gate and must be stopped or upgraded.

Future migrations must preserve originals, be safe to retry, and use verified copy-on-write publication or a durable backup/recovery path for payload changes. The marker commits only after a step succeeds. Never remove released migration steps.
