# Global cloud data contract

Each WebDAV sync root has one unencrypted `data-contract.json` containing `{"dataContractVersion":1}`. This is the authoritative global cloud contract. The app target is `CLOUD_DATA_CONTRACT_VERSION` in `monitor_cloud.py`, also declared as `cloudDataContractVersion` in `package.json` and packaged `version.json`. Object-level format identifiers remain for decoding and validation; they do not independently authorize access or trigger global upgrades.

Every logical cloud operation checks the marker before accessing payloads. It then acquires an exclusive WebDAV write lock on the root with `Depth: infinity`, rechecks the marker under that lock, and retains the lock until the operation (including nested account, skills, and usage requests) finishes. Only one operation may hold that root lock. A busy root fails the operation so manual requests can be retried and automatic synchronization can retry on its next scheduled run. Lock requests and migration requests remain inside the existing operation's single start/end notification pair.

- Equal version: permit normal reads and writes under the lock.
- Lower version, including an absent marker treated as zero: run every pending `CLOUD_DATA_MIGRATIONS` step consecutively, commit each version with conditional PUT, and verify it before proceeding.
- Higher version: block payload reads, writes, destructive overwrite, and passphrase rotation; report that the local script needs an update. Reading the contract marker itself is necessary to make this decision. Updating the app is handled by the existing updater, not by the cloud contract gate.
- Invalid metadata, missing migration steps, or unavailable lock support: fail closed rather than guessing a version or falling back to optimistic writes.

The initial migration (0 to 1) registers the existing saved formats without modifying any account, skills, usage, encryption, or historical payload. Its only persistent change is creating the global marker. It does not claim to convert previously unsupported legacy usage layouts into usage v4. Local contract 12 is already pending, so this cloud metadata change belongs to that same unreleased change. Offline local startup remains available; the cloud migration runs automatically on first cloud access, before affected cloud data is used.

Future migrations must preserve originals, be safe to retry after interruption, and use verified copy-on-write publication or a durable backup/recovery path for any payload changes. The registry does not automatically roll back arbitrary remote mutations. The version marker commits only after the step succeeds; failure retains the last committed version. Never remove released steps. A pending cloud migration should absorb further unreleased cloud changes, following the same release-boundary rule as the local contract.

The lock requests a 300-second lease and requires the server to return a finite timeout exceeding 60 seconds. Requests refresh the lease halfway through it and submit the lock token in a tagged `If` condition on the root. An expired lease stops further payload access; it is never silently reacquired in the middle of an operation. A process crash therefore releases access after the server's lease expires, and another client can retry the uncommitted step. Infinite leases are rejected. Normal completion and exceptions explicitly unlock. This requires RFC 4918 exclusive recursive locking, strong ETags, and conditional writes; `allowOptimisticWrites` cannot bypass contract protection.

Cloud overwrite preserves the root collection and global marker and deletes only its other children, keeping the root lock valid. Passphrase rotation leaves the unencrypted marker unchanged. Clients released before this feature cannot honor the new global version gate; update every participating client. Server-side locks exclude their conflicting writes while a protected operation is active, but cannot retroactively prevent their reads or enforce a version check after the lock is released.
