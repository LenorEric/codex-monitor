# Testing

- Run commands from the repository root with Python 3.12+ and Node.js. Install Python dependencies with `python -m pip install -r requirements.txt`.
- Run focused Python tests with `python -m unittest test_<module>`; run the Python suite with `python -m unittest discover -p "test_*.py"`.
- For dashboard changes, run `node test_dashboard_loading.js`; for extension syntax, run `npm run check`.
- `npm test` currently references the missing `test_management_queue.js`; use the Python suite and dashboard command directly until that script is repaired.
- Isolate integration fixtures from real credentials and saved data. `CODEX_HOME` changes Codex inputs but does not relocate the monitor's `~/.codex-switch` store; use explicit temporary roots or patched path helpers.
- Stop every test instance after the test finishes, including instances started for live traffic or integration testing.

# Runtime and packaging

- The VS Code extension connects to the Python service; it does not launch it. Start the service separately with `python codex_monitor_daemon.py` (`--dashboard` also opens the browser).
- Edit runtime sources at the repository root. `release/runtime/`, release manifests, VSIX files, and `release_pack/` archives are generated by `build_release.py`; runtime and package README templates are `release-runtime.md` and `release-package.md`.
- Run `python build_release.py` only for an explicit release: it increments the package patch version, rebuilds artifacts, removes older packages, and runs `git add --all` followed by a release commit, including unrelated working-tree changes.

# Data boundaries

- Keep ingestion and business calculations in the Python backend. Dashboard and extension clients consume prepared account-based bulk snapshots and sequenced WebSocket updates; `/api/series` is retired (410).
- Preserve canonical histories and synchronization ownership when rebuilding derived projections or delivery artifacts. Cloud-downloaded history must not be appended to local recorder files.
- Use `monitor_sample_store.connect()` when querying compatibility views such as `processing_facts`, `local_records`, and `remote_records`; their JSON columns require registered codec functions. Plain SQLite clients should inspect typed physical tables.
- Consult `data-pipeline.zh-CN.md` for pipeline semantics, `sampled-storage.md` for typed storage, and `dashboard-delivery.md` for delivery behavior. Verify version claims against code and successful releases; design documents contain historical targets.

# WebDAV notifications

- Emit exactly one start/queued message and one end message for every logical WebDAV operation, including automatic synchronization. Report success or failure, and explicitly explain cancellation, skipping, or partial completion. Nested WebDAV requests must not duplicate these messages.

# Persistent data contracts

- Cloud data migrations must consolidate historical usage into chronological packs during final publication; do not upload intermediate per-day files merely to repack them afterward.
- Count uncompressed canonical UTF-8 JSON bytes. Seal a pack after appending a complete record makes it exceed 75,000,000 bytes, and place subsequent records in the next pack.
- Preserve daily logical hashes when record contents are unchanged. Packing alone must not invalidate verified client caches or rebuild projections.
- Resolve references across all dates and months, and retain each shared pack until no live reference remains.
- Update the data contract only when existing locally or cloud-saved data needs conversion, cleanup, or rebuilding because its persisted representation or meaning changes, including formats, schemas, field meanings, filenames, or derived data.
- Changes solely to reader/writer code, modules, libraries, or access methods do not require a contract update when existing saved data remains valid without modification. Transport-only client/server changes do not require a bump.
- Keep at most one unreleased migration: if the latest released contract is N, the pending target is N+1. Create it for the first persistent-contract change; merge all further unreleased changes into that same migration instead of incrementing again.
- Keep `package.json.dataContractVersion`, `DATA_CONTRACT_VERSION`, and the newest `DATA_MIGRATIONS` entry aligned. Packaging propagates the target to `release/runtime/version.json`; do not increment it merely for a build or a release without saved-data changes.
- A successful explicit release through `build_release.py` freezes the included migration. The next persistent-contract change then creates the next number. Failed builds, commits, tests, and generated runtime/manifest refreshes do not freeze a pending migration.
- Determine the released baseline from the last successful release, not working-tree metadata or refreshed `release/runtime` files. Never rewrite or merge migrations already released to users; leave every released intermediate version available for sequential upgrades.
- The pending migration must convert the latest released data directly to the final intended representation. Avoid repeated cache rebuilds and temporary schemas or indexes superseded before release.
- Rebuilds are optional migration work, never an automatic consequence of completing a migration. Preserve valid projections for representation-only changes; request a rebuild explicitly when changed data or calculation semantics make it useful.
- Use `request_migration_rebuild(paths, reason, sampling=...)` for explicit rebuild requests. Cascading migrations accumulate a durable pending flag; publish one final projection rebuild request and replay sampling only after the whole cascade succeeds. Preserve pending work on failure and retry.
- Use explicit sampling/projection rule versions for semantic invalidation; do not hash whole source files or rebuild merely because code changed. Migration steps may request targeted work instead of invalidating all histories.
- Every migration must cover existing data by preserving it or safely rebuilding an equivalent representation from retained sources. Preserve originals on failure, make retries safe, and run pending steps consecutively on first startup before affected data is used.
