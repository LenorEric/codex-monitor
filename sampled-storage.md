# Sampled storage and dashboard interpretation

New local quota records use `quotaRunVersion: 1`, with new records created independently per window. A compatible legacy tail can retain both windows under its original identity; each window has independent bounds. `checkedAt` identifies the first observation; window fields `firstAt`/`lastAt` are Unix seconds, `continuous` is the saved accepted value or null, `multiplier` is resolved at sampling time, and `resetBoundary` preserves synthetic reset barriers. These additional fields round-trip through the typed store's extension codec. A compatible observation changes only `lastAt` under the existing record identity. Sampling/projection caches contain runs, and interpretation consumes their bounds without another run-collapse pass. Existing legacy point histories remain valid. The pending local contract stays 21; cloud contract remains 4. The separate publication index retains original point records under their original identities; local run extensions never rewrite those publication records. Quota backup files are atomic local-run snapshots; token recorder behavior is unchanged.

Local contract 20 and the consolidated cloud contract 4 remove legacy token baselines and coverage metadata from active history. Runtime calculation and synchronization accept only current `usage` events. The local migration rebuilds affected events from retained SQLite source events when their identity and account attribution are known; otherwise it discards the unconvertible records and their references. Recorder JSONL is never read as a recovery source. Derived token totals and delivery state are rebuilt. Cloud migration removes baselines and their dependent events across day partitions and trusts successful PUT responses before committing the marker, without read-back or cloud rollback backups. Local migration failures retain originals for rollback and retry; discarded history does not contribute to new totals.

Pending local contract 20 also consolidates one-to-one sync, token totals, legacy session header fields, and independent 5h/7d quota observation readings (`usedPercent`, `percentCheckedAt`) into prefixed typed columns on `sample_records`, while virtualizing derived sample metadata (`subtype`, `account_id`, `origin_device_id`, `identity_session_id`). The runtime no longer creates `sample_sync`, `quota_samples`, `token_samples`, `baseline_sessions`, `processing_peer_rows`, or `delivery_members` child tables. Presence/type masks remain separate for each retained container. Retired quota compaction metadata is removed by pending local contract 20 and cloud contract 4; sample and transport hashes are updated without changing observation times or quota readings.

`quota_windows` now stores reusable period metadata (`account_id`, `origin_device_id`, `window`, numeric `resetAt`, and `plan`) keyed by period identity, while per-sample 5h/7d readings (`usedPercent`, `percentCheckedAt`) and Unix observation timestamps live directly on `sample_records`. `sample_records.five_hour_id` and `seven_day_id` reference shared `quota_windows` period rows so multiple observations within the same quota period share one period row. Each window's `percentCheckedAt` controls ingestion: a stale 5h window is retained at its original time when 7d refreshes. Partial updates at the same timestamp retain the sibling window. Sampling state advances only for observed windows. Transport envelopes keep their existing shape and hashes; cloud data needs no quota format conversion.

The layout conversion preserves sample IDs, ownership, attribution, payload hashes and existing projections. It verifies every reconstructed payload and foreign key inside a rollbackable transaction before retiring the old layout. Cleanup removes a period metadata row only after its final referencing sample is released. Existing records without independent timestamps retain their original shared observation time; migration does not invent historical timestamps.

Processed quota payloads are deduplicated in `processing_payloads` and referenced by `processing_sampled_quota_refs` and `processing_quota_point_refs` (exposed through compatibility views `processing_sampled_quota` and `processing_quota_points`). Local contract 21 clears obsolete `processing_display` and `processing_cost_ranges` data; their empty schema remains for sequential historical migrations. The projector prepares quota points and forwards ingestion work; current chart attribution is owned by the delivery interpretation layer. Contract 21 also requests a delivery-only attribution rebuild for the 600-second distance limit. Canonical histories, sampled quota, quota projections, and token totals are preserved; saved memberships/charts are recalculated and prepared snapshots regenerated with a fresh epoch so reconnecting clients replace old token aggregates. The explicit attribution rule version invalidates older delivery results once, including on restarts during development. `processing_effective_refs` stores references to `sample_records` instead of duplicating usage JSON payloads. `remote_record_refs.peer_position` tracks peer fact positions directly on remote references. `delivery_run_payloads`, `delivery_run_refs`, `delivery_token_payloads`, `delivery_token_refs` (storing `interval_5h` and `interval_7d` inline), and `delivery_charts` contain typed, account-scoped interpretation state shared across `local` and `merged` views via `delivery_runs` and `delivery_tokens`. `delivery_journal` commits sequenced changes with that state; `delivery_snapshot` holds the serialized/gzip bulk. Historical baseline tables/codecs remain for ordered upgrades only; current calculation does not consume them.

# Sampled storage, pending local contract 16

`monitor_sample_store.py` owns normalized payload storage and reconstruction. `monitor_ingestion.py` tracks and parses original Codex session files; `monitor_processing.py` provides database access and transactional processing state. Quota and token records go directly into SQLite. The same transaction queues independent write-only JSONL output in `processing_backup_queue`; `monitor_backup.py` appends without reading or repairing recorder files. Log failures do not roll back committed facts, and queued appends retry. Corrections append ordinary updated records. Database removals do not generate log entries; explicit rebuilding applies current processing rules to logged records. Diagnostic sample logs are no longer written, and their CLI options have been removed. Existing diagnostic files remain available for historical inspection and released migration compatibility. Manual rebuilding is external; the application contains no recovery reader or manual rebuild logic. Normal ledger ingestion commits records, checkpoints, notifications and backup queue entries together without saving a second prepared ledger batch. Migration 19 finishes batches left by released runtimes. `monitor_sampling.py` owns deterministic backend decisions. Raw facts, processed points, per-window protection state, and source checkpoints survive restart in SQLite.

Recognized payloads have no stored full JSON copy. Presence, null, float and boolean masks reproduce absent/null distinctions and original numeric types. Small container markers preserve empty, missing and null structures; extension sidecars preserve unknown fields. Exceptional numeric values that SQLite would coerce are preserved in extensions. Unknown record kinds remain opaque. Timestamp text and Python float precision are retained.

Source-specific slot/label fields are factored out before payload hashing and restored from each owner's attribution. Only identical remaining canonical payloads share a sample; conflicting versions retain different samples. Local synchronization hashes remain hashes of the complete original transport record. Owner replacement/deletion queues the old sample for indexed cleanup in the same transaction; another owner's reference prevents deletion.

The old `processing_facts`, `local_records` and `remote_records` names are SQL views. Their JSON columns are computed by the repository codec and occupy no payload storage. Internal callers use `monitor_sample_store.connect()` to register those functions. For direct SQL inspection with a normal SQLite client, query the typed physical tables instead. Processing predicates use typed ownership fields, including a source/session index and a typed legacy-baseline partial index.

Migration streams 256 owners per batch inside one SQLite transaction. It verifies every reconstructed record, synchronization hash, owner count and foreign key before dropping the old tables. Startup's existing backup/journal wraps the conversion and subsequent processing initialization. A failed conversion does not advance the contract marker; an interruption after commit but before marker update restores the original database on restart. JSONL, parser checkpoints, prepared ledger batches, slot order and remote ownership are retained.

## Measured database snapshot

The 2026-10-26 benchmark used a consistent backup of the current `usage_monitor_sync_cache-v4.sqlite3`. It converted 104,154 processing facts, 77,707 local records and 26,271 remote records to 104,154 shared samples. Migration took **171.7 seconds** on this machine. Per-record verification is included; the outer startup backup duration is excluded.

| Allocated sampled storage | Before | After |
| --- | ---: | ---: |
| Tables, including dictionaries and ownership | 204.72 MiB | 79.91 MiB |
| Indexes | 115.16 MiB | 96.66 MiB |
| Total | **319.89 MiB** | **176.57 MiB** |

The reduction is **44.8%**, or 143.32 MiB. These are SQLite `dbstat` allocations, including overflow pages and automatic indexes, excluding unchanged processing/chart caches. Dropped pages enter SQLite's freelist; existing incremental vacuum reclaims file space gradually. The live database was not modified by the benchmark.

| Query, warm median of seven runs | Before | After |
| --- | ---: | ---: |
| Source/position payload, one row | 0.022 ms | 0.157 ms |
| Account's latest 100 quota records | 0.147 ms | 5.599 ms |
| Source/session lookup, one matching row | 201.888 ms | 0.148 ms |
| Remote day partition, 100 envelopes | 0.152 ms | 7.159 ms |

JSON reconstruction adds CPU cost to payload reads. Metadata-only existence checks do not reconstruct samples. Idle processing retains its incremental checkpoints; cleanup visits release candidates rather than scanning sample history. The source/session lookup now uses its dedicated typed index.

Machine-readable table/index sizes, query plans and complete owner-history fingerprints are in `sample-storage-benchmark.json`. Reproduce on a fresh copy with `python benchmark_sample_storage.py SOURCE.sqlite3 NEW_COPY.sqlite3 REPORT.json`; APSW supplies `dbstat` when the system sqlite3 module lacks it. The command refuses to overwrite its copy destination.

Validation covers exact canonical/hash round-trips, unknown envelope kinds, compaction, legacy high-waters, numeric precision, missing/null fields, sharing, conflicting versions, source attribution, final-reference cleanup, failed conversion, journal recovery and retry. Existing ingestion, correction, source replacement, retention, projection, synchronization and idle/restart tests exercise the new repository paths. Python suite: 627 tests passed with one existing skip; JavaScript suites: 28 tests passed. Test processes terminate after completion.
